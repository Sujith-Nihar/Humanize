# ADR-040 — Browser client as a separate product surface (BrowserText)

Status: accepted, scoped to architectural investigation and design only. This ADR knowingly
deviates from the upstream specification's Phase 1 exclusion of browser extensions
([spec line 35](../spec/Humanize_Final_Engineering_Build_Spec.md), line 2049, line 2091), and
records that deviation explicitly rather than changing the architecture silently, per
[AGENTS.md](../../AGENTS.md)'s requirement to surface conflicts with the preserved specification.
It does not approve implementation of extension code, a new API surface, a new schema, or any
change to `apps/api`, `packages/domain`, `packages/review`, or GitHub publication.

## Context

Humanize currently reviews user-visible repository content originating from GitHub pull
requests. The whole pipeline — extraction, routing, review, verification, ranking, suggestions,
publication — is anchored to a GitHub App installation, a specific repository, and a specific
commit. A browser extension is being proposed as a future, separate product surface: a user
explicitly selects text in their browser (a CMS field, a docs editor, a web app's copy) and asks
Humanize to review it, outside the context of any pull request.

A read-only architectural discovery preceded this ADR and found: no existing API endpoint accepts
arbitrary extracted text ([`apps/api/src/app.ts`](../../apps/api/src/app.ts),
[`apps/api/src/runner.ts`](../../apps/api/src/runner.ts)); the runner and GitHub packages are
GitHub/Git-shaped end to end; and the upstream specification names browser extensions explicitly
as out of Phase 1 scope. This ADR is the required record of that conflict and of the decision to
proceed with investigation and design despite it.

## Current architectural limitation

`ReviewSnapshot` ([`packages/domain/src/index.ts:74`](../../packages/domain/src/index.ts)) is a
GitHub-App-installation record: it requires `installationId`, `owner`/`repository` (regex-validated
GitHub identifiers), `pullNumber`, and `baseSha`/`headSha`/`configSha` all pinned to a real commit
history. There is no pull request, installation, or commit behind a piece of text a user selects
in their browser, so a `ReviewSnapshot` cannot be constructed for it without inventing fictitious
values — which would corrupt the very invariant the type exists to enforce (INV-010: findings
must never be published against a stale or wrong head).

`ContentNodeSchema` ([`packages/domain/src/index.ts:24`](../../packages/domain/src/index.ts))
requires `repositoryId`, `commitSha`, `blobSha`, and a repository-relative `filePath` validated by
`safePath`. These fields are not incidental metadata: `reviewNodes`
([`packages/review/src/pipeline.ts:106`](../../packages/review/src/pipeline.ts)) throws
`NODE_OUT_OF_SNAPSHOT` when a node's `repositoryId`/`commitSha` do not match the snapshot it is
reviewed under, and `validateRunnerResult`
([`packages/domain/src/index.ts:167`](../../packages/domain/src/index.ts)) independently rejects
`NODE_NOT_AT_HEAD`/`NODE_FOREIGN_REPOSITORY`. These checks are load-bearing security properties
(INV-004, INV-014: coordinates and identity come only from parsers/diffs against a real
repository, never asserted by a model or an untrusted caller), not formality. Browser-originated
text has no blob, no commit, and no repository, so it cannot satisfy `ContentNodeSchema` without
fabricating identity fields that the rest of the system treats as trust anchors.

Both types are therefore unsuitable, by design, as a home for browser-originated text. Weakening
either schema to accept it (for example, by making the identity fields optional) would degrade
the guarantees the GitHub review path depends on for every existing task. This ADR treats that as
disqualifying and requires a new, separate concept instead (see below), rather than a relaxation
of `ContentNodeSchema` or `ReviewSnapshotSchema`.

## Proposed decision

Authorize investigation and future implementation of a browser client as a **separate product
surface**, additive to the existing GitHub App, without weakening any existing GitHub-path
invariant.

The browser surface must NOT:
- replace the GitHub review path;
- bypass review verification (the reviewer/verifier separation and the deterministic evidence
  gate in [`packages/review/src/pipeline.ts`](../../packages/review/src/pipeline.ts) apply
  identically);
- call model providers directly from the browser;
- receive provider secrets in the browser or in extension code;
- reuse runner credentials (see Authentication);
- silently fall back from local to cloud execution (INV-007 applies unchanged);
- claim model output is authoritative (INV-006 — no assertion of AI authorship — applies
  unchanged, and no browser finding may claim certainty either);
- automatically modify page content.

The existing GitHub ingestion, extraction, review, verification, ranking, and publication code
paths are unchanged by this decision. No file under `apps/api`, `apps/worker`, `apps/runner`,
`packages/github`, `packages/scanner`, `packages/config`, or the review pipeline's GitHub-specific
callers is modified by this ADR or is authorized to change as a consequence of it alone.

## New conceptual source type

Introduce the concept of **`BrowserText`**: explicitly user-selected text that has no repository
identity. This is a naming and boundary decision only; the schema is intentionally **not**
implemented by this ADR.

Conceptual fields such a type will eventually need to carry (non-binding, subject to design):
- `text` — the user-selected content itself, bounded in size.
- `characterRange` — the selection's start/end offsets within its source, analogous in spirit to
  `SourceRangeSchema` but without claiming repository-anchored authority.
- `sourceType` — a discriminator for where the text came from (e.g. a generic web page field, a
  specific supported CMS/editor integration), since the trust and structure of the source differs.
- `originMetadata` (optional) — non-identifying context such as page origin/host, deliberately
  excluding anything that could re-identify a private repository or leak page contents beyond what
  the user selected.
- `requestIdentity`/`sessionIdentity` — an identifier binding the text to one review request or
  session, for idempotency, rate limiting, and abuse tracking, without implying tenant or
  organization membership until that is separately decided (see Open questions).

`BrowserText` must **not** be forced into `ContentNodeSchema`. It is a distinct type with its own
schema, its own validation, and — because it has no commit/blob/file to revalidate against — its
own, more limited notion of what a "finding" or "suggestion" can safely mean (see Suggestions).

## Review architecture

The intended future boundary, once designed and separately approved for implementation:

```
Browser Extension
    ↓
Browser Review API          (new, narrow endpoint family; not /webhooks/github, not /runner/*)
    ↓
BrowserText                 (new schema; no repository/commit/blob identity)
    ↓
review/domain-compatible review path   (reuses routeNode/reviewNodes-shaped logic, rules, ranking)
    ↓
existing provider abstraction          (@humanize/providers, server-side only)
    ↓
validated findings          (comment-only; see Suggestions)
    ↓
Extension
```

The existing GitHub pipeline (`webhook → review run → runner lease → executor → RunnerResult →
control-plane validation → ranking → publication`, as documented in
[HANDOFF.md](../implementation/HANDOFF.md)) remains entirely unchanged and runs independently of
this surface. The intent is to reuse `@humanize/rules`, `@humanize/review`'s reviewer/verifier
gate, and `@humanize/providers`'s adapters against `BrowserText`-derived input, not to build a
second review engine (see Alternatives considered).

## Suggestions

The existing `SafeSuggestion` mechanism ([`packages/suggestions/src/index.ts`](../../packages/suggestions/src/index.ts))
cannot be directly reused for browser editors. Its safety proof depends on re-parsing a real
repository file with `@humanize/extractors` and asserting that exactly one `ContentNode`'s text
changed and nothing else about the file's structure did
([`packages/suggestions/src/index.ts:48`](../../packages/suggestions/src/index.ts)). A browser
selection is not a file Humanize can re-extract and structurally diff; there is no equivalent
proof available for an arbitrary web page field or editor buffer today.

**For the initial browser MVP, this ADR recommends findings-only behavior**: explanations and
(at most) a proposed replacement string shown to the user for their own manual action. This ADR
does **not** authorize automatic text replacement, a one-click apply, or any new structural-safety
mechanism for browser content — that would require its own design and its own ADR once a specific
editor/CMS integration is scoped.

## Authentication

- **Runner credentials are inappropriate.** They identify a specific enrolled, tenant/repository-scoped
  runner process authorized to execute leased GitHub jobs
  ([`apps/api/src/runner.ts`](../../apps/api/src/runner.ts),
  [`docs/architecture/runner.md`](../architecture/runner.md)); a browser extension is a different
  actor class entirely, with no lease, no fence, and no repository to scope to.
- **Dashboard session cookies are not an appropriate extension credential.** `SessionSigner`
  ([`packages/security/src/index.ts:35`](../../packages/security/src/index.ts)) is designed for a
  same-origin, cookie-based browser flow against the dashboard; an extension's background/service-worker
  context does not share that origin or cookie jar by default, and reusing session cookies would
  blur a credential meant for administrative dashboard actions into a different, higher-volume,
  higher-exposure use case.
- **A dedicated extension/user authorization model must be designed** before any implementation.
  This ADR does not specify or implement one; it only rules out the two existing mechanisms as
  unsuitable. Candidate shapes (e.g. a personal, revocable, rate-limited token issued through the
  existing dashboard session, distinct from both runner and session credentials) are left as an
  open question.

## Privacy

Browser text must be treated as potentially sensitive by default: it may originate from private,
unpublished, or confidential content the user is drafting anywhere on the web, with no repository
enablement or administrator policy to gate it the way GitHub-path content is gated today. Default
behavior must be **ephemeral processing** — reviewed and discarded, not persisted — unless the
user explicitly opts into retention. This mirrors, but does not reuse, the existing ephemeral
retention mode's intent ([`packages/db/src/publication.ts`](../../packages/db/src/publication.ts),
ADR-038): content should not outlive the request that needed it by default.

## Abuse protection

Arbitrary-text review is a new public abuse and cost surface, structurally unlike the existing
GitHub-gated paths: today, review only runs against repositories an administrator has explicitly
enabled ([`packages/db/src/administration.ts`](../../packages/db/src/administration.ts)), which
bounds both who can trigger a review and how often. A browser endpoint accepting arbitrary text
from any installed extension has no equivalent bound. Before any production exposure, this surface
requires, at minimum: authentication (see above), rate limiting, per-user/per-key quotas, and
request-size limits, none of which exist yet for any endpoint in this codebase (the existing
adversarial review, S19-T02/T03, already records the absence of a global rate limit even for the
current GitHub-gated endpoints as an open gap). None of this is implemented by this ADR.

## Scope

This ADR authorizes the architectural work required to investigate and design support for a
browser extension as a separate product surface: naming the `BrowserText` concept, defining the
intended data-flow boundary, and ruling out unsuitable reuse of existing GitHub-anchored types and
credentials. It does **not** authorize:
- implementing `BrowserText` or any new schema,
- creating a new API route, package, or `apps/extension`,
- installing any dependency,
- modifying `ContentNodeSchema`, `ReviewSnapshotSchema`, or any GitHub-path code,
- bypassing any existing Phase 1 security invariant (INV-001 through INV-016 continue to apply in
  full to both the existing GitHub path and any future browser path).

Any of the above requires a further, separate implementation decision — and, for anything touching
architecture, its own ADR — once the open questions below are resolved.

## Alternatives considered

1. **Put the extension directly into the existing GitHub review pipeline.** Rejected: the pipeline
   is built around `ReviewSnapshot`/`ContentNode` identity anchored to a GitHub installation,
   repository, and commit (see Current architectural limitation). Forcing browser text through it
   would require fabricating repository/commit/blob identity, corrupting the trust anchors that
   `validateRunnerResult` and `reviewNodes` rely on for every existing GitHub-path guarantee.
2. **Call OpenAI/Gemini directly from the extension.** Rejected: this puts provider secrets in
   browser-reachable code, which ADR-035 already forbids for the dashboard's credential UI for the
   same reason (*"never saved-secret readback, browser storage, analytics, bundling or browser
   provider calls"*), and it bypasses the entire verification/evidence-gate architecture that makes
   a Humanize finding trustworthy rather than a raw, unverified model response.
3. **Reuse runner credentials.** Rejected: runner credentials authorize execution of leased,
   tenant/repository-scoped GitHub jobs under the outbound lease protocol
   ([`docs/architecture/runner.md`](../architecture/runner.md)); they carry no notion of an
   individual browser user or an arbitrary-text request, and stretching their scope would weaken
   the isolation the lease/fence protocol exists to guarantee.
4. **Create an entirely separate review engine** for browser text (its own rules, its own
   provider calls, its own verification). Rejected: this duplicates the reviewer/verifier
   evidence-gate logic, the deterministic rule families, and the provider adapters that already
   exist, doubling the surface that must be kept correct and consistent, and risking silent
   divergence in what Humanize considers a defensible finding between the two paths.
5. **Add a browser-specific input layer while reusing the existing review/provider
   infrastructure.** This is the preferred approach. It introduces exactly one new concept
   (`BrowserText`) and one new boundary (a browser-facing API), while reusing
   `@humanize/rules`, the reviewer/verifier gate in `@humanize/review`, and the provider adapters
   in `@humanize/providers` unchanged in their review logic. It keeps the GitHub path's identity
   guarantees intact by never asking `ContentNodeSchema`/`ReviewSnapshotSchema` to represent
   something they were not designed to represent, and it avoids the duplication and drift risk of
   alternative 4 while avoiding the invariant-weakening of alternatives 1 through 3.

## Consequences

**Positive:**
- Establishes a boundary that lets a browser surface be designed and eventually built without
  touching or risking the GitHub review pipeline's correctness or security properties.
- Reuses the verified reviewer/verifier evidence gate and deterministic rule families instead of
  duplicating them, so review quality and safety properties (INV-003, INV-006, INV-013) extend to
  browser text rather than being reinvented and re-proven from scratch.
- Records, rather than silently overrides, the upstream specification's Phase 1 exclusion of
  browser extensions, satisfying AGENTS.md's conflict-surfacing requirement and leaving a clear
  trail for anyone auditing why this surface exists despite that exclusion.

**Negative:**
- Introduces a second, structurally different notion of "reviewable content" (`BrowserText`
  alongside `ContentNode`), which is additional conceptual surface area to maintain and keep from
  drifting apart from the GitHub path's semantics over time.
- Cannot offer the one-click, structurally-proven suggestion experience the GitHub path offers;
  the initial browser experience is necessarily weaker (findings-only) until a separate safety
  mechanism for arbitrary editors is designed.
- Adds a new authentication mechanism, a new public-facing abuse surface, and a new privacy/retention
  decision to design and operate, none of which the current system has needed to solve for the
  GitHub-gated paths.
- Remains, by the upstream specification's own terms, an explicitly out-of-plan surface; if the
  specification is later revised upstream, this ADR and any resulting design must be reconciled
  with that revision.

## Open questions

- The exact `BrowserText` schema (field names, size limits, validation rules, versioning).
- The authentication mechanism for the browser client (issuance, revocation, scope).
- Whether/how a browser request associates with a tenant or organization, or remains fully
  unaffiliated.
- The retention model in detail: what "explicit opt-in" means operationally, where opted-in data
  would be stored, and its lifetime.
- Whether any browser suggestion safety model can ever be built, and if so, what it would need to
  prove in place of `@humanize/suggestions`' repository-file re-parse.
- Rate limiting and quota mechanics (per-user, per-installation, global) and where they are
  enforced.
- Which browsers/extension platforms are in scope.
- Whether and how the local Humanize Runner could ever execute a browser-originated review (for
  users who want browser text kept off cloud providers), given the runner currently only executes
  GitHub-lease-bound jobs (see [`docs/architecture/runner.md`](../architecture/runner.md)).
