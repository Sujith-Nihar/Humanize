# ADR-038 — Transient publication payloads

Status: accepted. Required to make asynchronous publication possible at all; the alternative designs were rejected for the reasons below.

## Current design

A runner uploads a result, the control plane validates it, and publication is scheduled rather than performed inline, so that a runner never waits on GitHub and a failed publish is retried by the durable queue.

Findings are persisted in the `findings` table, but a database constraint requires that in ephemeral retention mode `explanation` and `replacement` are null. Only operational metadata and digests are kept. The accepted result itself is not stored at all.

## Problem and consequence

A worker that picks up a scheduled publication cannot reconstruct what to publish. The explanation text, the quoted content and any suggestion exist only in the HTTP request that has already been answered. Asynchronous publication is therefore impossible as things stand, and the choice is between three unattractive options.

Publishing inline in the request would make a runner wait on GitHub and would lose the entire review if the publish failed, since the result cannot be recovered. Holding results in process memory would lose them on restart and would not survive more than one control-plane instance. Persisting findings with their text in ephemeral mode would break the retention promise the mode exists to make.

## Decision and alternatives

Introduce `publication_payloads`: a single row per review run holding the validated, publishable payload, written when a result is accepted and **deleted as soon as publication completes or is abandoned**. The row carries the run's retention mode and an expiry, and a retention sweep removes anything left behind by a crash.

This is consistent with the specification's own words for ephemeral mode, which require repository content context to be rebuilt per review and **deleted after the job**, rather than never written. The promise the mode makes is that no content survives the job, not that content never touches storage; the ephemeral guarantee becomes a lifetime guarantee, which is enforceable and testable, rather than an absolute that would make asynchronous publication impossible.

Alternatives were rejected as above: inline publication trades away durability, in-memory handoff trades away both durability and horizontal scale, and persisting findings permanently breaks the retention mode outright.

## Implementation impact

A migration adds `publication_payloads` with the tenant and run foreign keys the other tables use, an `expires_at`, and the retention mode copied from the run. The publish worker reads the row, publishes, and deletes it in the same transaction as recording the published comment identifiers. A maintenance sweep deletes expired rows so a crashed publish cannot leave content behind indefinitely.

## Verification and approval evidence

Five PostgreSQL integration tests in `packages/db/publication.integration.test.ts`: a taken payload is gone after `discard`, an abandoned payload is discarded on the same path because unpublishable content is still content, an expired payload left by a crash is swept while a live one is untouched, a payload for a non-existent run is refused by the foreign key, and payloads are isolated by tenant. The migration `0004_famous_fixer.sql` applies from a freshly created disposable database. Worker behaviour is now demonstrated too: five further tests in `apps/worker/publish.integration.test.ts` assert the payload row count directly after a successful publish, a superseded head, an unparseable payload, and a retryable failure where the payload is deliberately kept and then cleared by the retry. `apps/worker/src/main.ts` sweeps leftovers at startup, so content never outlives a crash by more than one restart.
