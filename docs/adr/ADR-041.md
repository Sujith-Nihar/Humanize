# ADR-041 — Amazon Bedrock as a fifth cloud provider

Status: accepted for the adapter, contract tests and live lane. The user asked for Bedrock support
on 2026-09-28 after the stage 1 measurement showed local generation, not round trips, bounds review
latency. Cloud execution in the worker is **not** part of this decision and remains unbuilt.

## Current design

`ProviderId` allows `openai`, `gemini`, `openrouter` and `ollama`. The three cloud adapters share
`JsonProvider`: a projected JSON Schema is sent, and every response is validated locally against
the Zod schema, with one invalid-output repair, bounded transient retries and a 90 second cloud
deadline. `ReviewSnapshot` already distinguishes `cloud` from `runner` execution, and runner jobs
may use only Ollama (INV-007).

## Problem and consequence

On an Apple M3, `llama3.2` generates 12–14 tokens/s, and a 12-node review needs about 7,000 output
tokens: roughly ten minutes however calls are batched (see
[HANDOFF](../implementation/HANDOFF.md), 2026-09-28). The team has AWS Bedrock access and an API key
but no key for the three supported cloud providers, so no cloud model can be measured at all.

## Decision and alternatives

Add `bedrock` to `ProviderId` and a `BedrockProvider` adapter on `JsonProvider`:

- **API.** Converse, `POST /model/{modelId}/converse`, with the model id encoded as one path
  segment. System prompt in `system`, reviewed content in one user message.
- **Authentication.** A Bedrock API key as `Authorization: Bearer`, never in the body. AWS
  recommends short-term keys (up to 12 hours) for production and long-term keys for exploration
  only; the development lane reads the documented `AWS_BEARER_TOKEN_BEDROCK` variable.
- **Endpoint.** Fixed to `https://bedrock-runtime.{region}.amazonaws.com`. The region is validated
  against a strict pattern before any URL is built, and redirects are refused by the base adapter,
  so neither a model id nor repository content can move a request to another host.
- **Structured output.** Native `outputConfig.textFormat` of type `json_schema`, the same
  schema-constrained approach as the other cloud adapters. Bedrock accepts only a JSON Schema
  subset and rejects length, numeric and item-count keywords, so those are removed from the schema
  **sent**, and `minItems` above 1 is lowered to 1. Validation is unchanged: every response is still
  parsed against the full Zod schema locally, so a limit Bedrock was not told about is still
  enforced, and a violation goes through the ordinary single repair.
- **Errors.** Guardrail and content-filter stops are `REFUSAL` (never repaired); `max_tokens` and
  `model_context_window_exceeded` are `CONTEXT_LIMIT`; malformed output is `INVALID_OUTPUT`. HTTP
  424 (`ModelErrorException`) joins 408 and 5xx as retryable `TRANSPORT`. A 400 is
  `UNSUPPORTED_CAPABILITY`, which is what a model without structured-output support returns.
- **No fallback.** A model that does not support structured output fails its capability probe.
  The adapter does not silently switch to forced tool use, another model or another provider.

Alternatives rejected:

- **Forced tool use** (`toolConfig` with `toolChoice`). Works on more models, but constrains the
  output less strictly and would make this adapter behave unlike the other three. It can be added
  later as an explicit, probed mode if a needed model lacks structured output.
- **Bedrock's OpenAI-compatible endpoint through the existing OpenAI adapter.** That adapter uses
  the Responses API on a fixed OpenAI host; Bedrock's compatibility layer covers a subset of models
  and endpoints, so it is not a drop-in.
- **SigV4 with IAM credentials.** Better for production, but it needs request signing and a
  credential chain. It is left for the worker's cloud path, where short-lived credentials belong.

## Implementation impact

- `packages/providers/src/bedrock.ts`, exported with `bedrockSchema`; `ProviderId` gains
  `bedrock`, which `packages/config` and `apps/api` administration inherit. The provider column
  is `text`, so no migration is needed.
- `packages/providers/src/errors.ts` maps 424 to retryable `TRANSPORT`. No existing provider
  returns 424.
- Live lane: `packages/providers/bedrock.live.test.ts`, and `evals/review/live-provider.ts` selects
  Bedrock for the batch and gate evaluations only when its variables are set explicitly.

Unchanged and still required before any customer repository is reviewed by Bedrock:

- A worker executor for `cloud` jobs; today only the Ollama runner executes reviews.
- Credential plumbing: `apps/worker` sets `credentialRef:null`, so a saved key never reaches a job.
- Organization opt-in for cloud execution, and a data-handling review of sending repository text
  to AWS in the administrator's chosen region.

## Risks

- Bedrock compiles a grammar for each new schema, which the documentation says "may take up to a
  few minutes", then caches it for 24 hours. A first call can therefore exceed the 90 second cloud
  deadline and fail as `TIMEOUT`. The capability probe warms only the reviewer schema.
- Structured-output support varies by model and region. The documentation names Claude 4.5
  models and select open-weight models; the probe is the authority, not a list.

## Verification and approval evidence

- Mocked contract tests in `packages/providers/providers.test.ts`: request shape and fixed
  endpoint, key only in the header, region validation, schema stripping with local validation
  still enforced, stop-reason and HTTP error normalization, bounded retries, and the capability
  probe.
- **No live Bedrock call has been made.** Live acceptance requires `AWS_BEARER_TOKEN_BEDROCK`,
  `HUMANIZE_BEDROCK_REGION` and `HUMANIZE_BEDROCK_MODEL`, then
  `pnpm exec vitest run --config vitest.live.config.ts packages/providers/bedrock.live.test.ts`.
