# ADR-044 — A reported limit on changed content per review

Status: accepted. Resolves audit finding B5 in
[audit-2026-09-29](../implementation/audit-2026-09-29.md).

## Current design

The executor selected the changed nodes of a pull request and then applied `LIMITS.nodeBatch`
(20) to the whole set. `nodeBatch` is the number of nodes that share one model call, and the
pipeline already batches by it.

## Problem and consequence

Applied to the whole pull request, the batch size became a silent cap. Every changed node after
the twentieth, in repository path order, was skipped, and no diagnostic, summary line or check
output said so. A pull request touching 200 strings was reviewed at 10% while reporting either its
findings or "Nothing to flag". That contradicts the architecture's rule that limits produce
explicit partial coverage, never silent success. The order was path order, so a configured
blocking rule on a later file could be skipped as well.

## Decision and alternatives

A review takes at most `LIMITS.changedNodesPerReview` (200) changed nodes. When a pull request
exceeds it:

- **Rule-governed content goes first.** Nodes that a configured blocking or standalone rule
  applies to are taken before others, so the limit never decides whether the customer's own
  policy is enforced.
- **The shortfall is reported.** It appears as `CHANGED_NODES_NOT_REVIEWED`, placed first in the
  result's diagnostics so the cap on diagnostics can never hide it.
- **Publication says so.** The summary states how many changed pieces were not reviewed. The check
  run is `neutral` and titled "Partially reviewed". It is never `success` with "No content issues
  found", which would claim more than was checked. A blocking finding still fails the check.

Rejected alternatives:

- *No limit.* One very large pull request would be unbounded in model cost and time, and
  `LIMITS.jobMs` is not yet enforced, so nothing else would stop it.
- *Keep 20 and just report it.* Reporting it would be honest, but 20 is far below what an
  ordinary content pull request changes. 200 is ten batched reviewer calls: about a minute on a
  hosted model, and still long on a small local model.

## Implementation impact

`LIMITS.changedNodesPerReview` is added, and the architecture limits line lists it.
`@humanize/execution` exports `COVERAGE_CODE`. `buildReview` and `buildCheck` take the count of
content not reviewed, and the worker's publisher reads it from the result's diagnostics.

The count comes from the executor. A compromised runner could misreport it, which changes only the
wording of the summary and check. It cannot publish or suppress a finding, because rule findings
are recomputed by the control plane (ADR-043).

Not covered here, and still silent:

- `NODE_LIMIT_REACHED` on an individual file, which is counted but not surfaced.
- Changed content inside files over the size limit.

## Verification and approval evidence

A runner executor test changes 205 paragraphs, with the one a blocking rule applies to placed
last. The review takes 200 nodes, the blocking finding survives, and the first diagnostic reports
five nodes not reviewed. The published summary and check say the review was partial. With the old
cut restored, the test fails at 20 nodes. A publisher test shows that a complete review with
nothing found is still `success`, and a partial one is `neutral` and never reads "Nothing to flag".
