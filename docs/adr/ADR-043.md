# ADR-043 — What crosses the boundary between execution and publication

Status: accepted and implemented. It resolves audit findings B1, B2 and B3 in
[audit-2026-09-29](../implementation/audit-2026-09-29.md). Each decision below is implemented in
its own commit, and the Implementation impact section records which ones are in.

## Current design

A review is executed in one place, a customer's runner or the cloud worker, and published in
another, the control plane. Two structures cross between them. The **snapshot** is fixed when the
run is created and tells the executor what to do. The **result** is what the executor hands back,
and the control plane validates it and turns it into published findings.

## Problem and consequence

Three things the review depends on did not cross.

1. **Context.** The result carried only the changed nodes, but evidence cites unchanged ones:
   the neighbouring paragraph, a near-duplicate, the heading a claim contradicts. Validation
   rightly refuses evidence naming a node it cannot see, so any finding that cited context
   invalidated the entire result, and nothing was published for the pull request.
2. **Settings.** Only a digest of the resolved configuration was in the snapshot. Categories,
   severity floor, inline cap, include and exclude, terminology, avoided phrases and blocking
   rules stopped at the event handler, so `.humanize.yml` and every review setting in the
   organization policy were ignored.
3. **Deterministic status.** Publication rebuilt every finding as model-proposed and
   non-blocking, so a blocking rule could never fail the check run, and rule findings were
   budgeted and filtered as if a model had proposed them.

## Decision and alternatives

1. **The result carries the context its evidence cites** (`contextNodes`), held to the same
   commit, repository and quotation checks as reviewed nodes. No finding may point at a context
   node. *Rejected alternative:* accepting evidence whose node is absent. It would have been
   smaller, but the control plane would then have to accept quotations it cannot check, and the
   runner is untrusted.
2. **The snapshot carries the resolved review settings, including path-scoped overrides.** The
   snapshot is already the immutable, digested record of what a run was asked to do, so the
   settings belong there rather than in a side channel. Both executors and publication read them
   from it. *Rejected alternative:* each executor re-resolving configuration itself. That would
   need the raw policy, which names credentials, to reach a customer's runner, and it would let
   two resolutions disagree.
3. **The control plane recomputes deterministic and blocking findings itself** from the reviewed
   nodes and the snapshot's settings, rather than accepting a flag from the executor. Rules are
   pure functions of text and settings, so recomputing them costs little and needs no trust in
   the runner. *Rejected alternative:* a `blocking` flag in the result. A compromised runner could
   then fail any customer's check run at will.

## Implementation impact

- Decision 1: implemented. `ReviewResultSchema.contextNodes` defaults to `[]`, so envelopes and
  stored payloads written before this change still parse. `execute.ts` sends exactly the nodes
  that surviving evidence names.
- Decision 2: implemented.
  - `ReviewSnapshotSchema.review` holds the repository-wide settings and one resolved set per path
    override. It defaults to the product defaults, so snapshots written earlier parse to what
    resolution would have produced for them.
  - `resolveReviewScope` produces it when the run is created, and `settingsForPath` answers for one
    file, with the first matching override winning, as resolution already chose.
  - The executor reads categories, the severity floor, include and exclude, visible props and
    calls, avoided phrases, terminology and blocking rules from it, per file. `ExecutionConfig`
    keeps only where and how large, so an executor can no longer supply its own settings.
  - Publication takes the inline cap from it.
  - The run's `configHash` now covers the whole scope, so changing only an override creates a new
    run rather than reusing one reviewed under other rules.
  - `allowDrafts` now takes effect.
  - Fixing this surfaced a resolution bug, also fixed: path overrides were merged shallowly, so an
    override naming one category re-enabled a category the repository had switched off. Mappings
    now merge key by key and lists replace.
  - A blocking rule now reaches nodes on paths where every review category is off. Previously the
    executor dropped such nodes before the rules ran.
  - Still with no effect: `voice.approved_sources` and `voice.tone`. Nothing downstream consumes
    them, so they are deliberately not carried.
- Decision 3: implemented.
  - `deterministicFindings` is the single definition of a rule finding, used by the pipeline and by
    publication.
  - `findingsFromResult` now requires the configured rules and recomputes rule findings from the
    reviewed nodes. It keeps the recomputed one where the executor also reported it as a candidate.
    The result envelope has no field that can mark a finding blocking.
  - `configuredRules` in `@humanize/execution` is the one composition of the snapshot's rules, used
    by both the executor and the worker's publisher.
  - Residual limit: the control plane recomputes over the nodes the result names. A compromised
    runner that omits a changed node therefore avoids its rules, because the control plane does not
    extract content itself.

Runners and the control plane ship from the same repository and are pre-release. A runner built
before this change still uploads valid results, which parse with an empty `contextNodes`.

## Verification and approval evidence

- Decision 3: five unit cases.
  - A rule finding is recomputed when the result omits it.
  - An executor duplicate collapses into one finding.
  - A result cannot promote its own candidate to blocking.
  - Content outside the reviewed commit is ignored.
  - Recomputed nits keep their exemption from the budget and the nit filter.
- The settings boundary test follows the real executor's output through publication to a
  `failure` check conclusion. With recomputation disabled, four tests fail, including that one.

- Decision 2: a runner executor test runs the real executor twice over one repository. With the
  defaults, every changed file is reviewed. With configured settings:
  - an excluded path is skipped;
  - a custom visible prop is extracted;
  - a blocking rule fires on a path whose categories are all off;
  - the model is never shown that path.
- Two resolution tests cover overrides, clamping and first-match. With the shallow merge restored,
  both fail.
- Two integration tests against PostgreSQL check that the stored snapshot carries the settings,
  that `allowDrafts` governs drafts, and that an override-only change is a new run.

- Decision 1: a runner executor test runs the real executor over a fixture repository whose
  changed paragraph repeats an unchanged one, with a model double that cites the neighbour's
  evidence. The result validates cleanly, and emptying `contextNodes` reproduces exactly
  `EVIDENCE_NODE_UNKNOWN`. With the executor change reverted, the test fails.
- Six validation cases cover context held to the same rules:
  - a quote absent from its context node is refused;
  - a foreign commit is refused;
  - a foreign repository is refused;
  - a duplicate identity across the two lists is refused;
  - a candidate pointing at a context node is refused.
