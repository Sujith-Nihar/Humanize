# Repository audit, 2026-09-29

A full read of the production source (about 8,000 lines across 18 packages and 5 apps), done at
commit 3f3f113 before continuing feature work. The goal was the question a reviewer asks of the
whole product rather than of one change: if a customer installs this today, does each feature do
what its documentation and task evidence say it does?

**Test status at the time of the audit:** `pnpm check` 416 unit tests across 52 files pass,
`pnpm build` passes, and all 79 integration tests pass against the disposable `humanize_test`
database. Green
tests are not the same as a working product. Most findings below sit *between* components that are
each tested alone: the unit and integration suites build their inputs by hand, so a field dropped
or never passed at a boundary does not fail any of them.

Severity: **Blocker** means a core feature does not work end to end. **Major** means wrong or
unsafe behaviour a customer would hit. **Moderate** means a real defect with a narrower trigger.
**Minor** is a small bug or rough edge. "Verified" means reproduced by running code; everything
else is established by reading the code at the cited lines.

## Blockers

### B1. A finding that cites repository context invalidates the whole review (verified)

The executor sends only the changed nodes in the result (`packages/execution/src/execute.ts:126`,
`nodes:changed`), but the evidence it attaches comes from the findings
(`execute.ts:108`), and most of that evidence is retrieved context that belongs to *other*,
unchanged nodes: neighbours, near-duplicates and related content (`packages/retrieval/src/index.ts`).
`validateRunnerResult` rejects any evidence whose `nodeId` is not in `result.nodes`
(`packages/domain/src/index.ts:198-201`).

Reproduced with a probe: two near-identical README paragraphs, only the second changed, one
repetition finding citing the first. Result: `violations: [ 'EVIDENCE_NODE_UNKNOWN' ]`.

Consequence: on the runner path the upload gets `422 INVALID_RESULT`, which the runner treats as
retryable, so the lease is retried three times and then fails for good. On the cloud path the run
is skipped as `invalid_result`. Either way **the entire pull request's review is discarded**,
valid findings included, and nothing is posted. The categories that most need context
(repetition, claim inconsistency, repository style) are the ones that trigger it. It was not seen in
live runs because those produced zero findings, and the evals call the pipeline directly without
the validation step.

### B2. Repository configuration and review policy never reach the review

`resolveConfiguration` computes categories, the severity floor, the inline comment cap,
include/exclude globs, visible props and calls, voice, terminology, avoided phrases and blocking
rules. `apps/worker/src/handlers.ts:101-115` then keeps only `configHash`, execution and retention
mode, and the model profiles in the snapshot. Nothing downstream can recover the rest:

- both executors enable every category unconditionally (`apps/worker/src/main.ts:51`,
  `apps/runner/src/main.ts:21`);
- rules run with an empty configuration (`execute.ts:100`, `config.rules??{}`), so terminology,
  avoided phrases and **blocking rules never fire**;
- publication calls `planPublication(findings)` with no cap (`apps/worker/src/main.ts:168`);
- exclude globs are never applied to scanning, so the default test/story/dist exclusions do not
  apply either.

In practice `.humanize.yml` and every review setting in the organization policy are ignored.
The comment at `apps/worker/src/main.ts:48-50`, added earlier in this session, says the snapshot
already applies the organization's permitted categories. It does not, and that comment is wrong.

### B3. Deterministic and blocking findings lose their status at publication

`findingsFromResult` rebuilds every finding with `deterministic:false, blocking:false`
(`packages/review/src/results.ts:24`), and the result envelope has no field to carry either flag.
So even once B2 is fixed, a blocking rule can never fail the check run (the ADR-017 contract in
`packages/github/src/publisher.ts:118`). Standalone deterministic findings (ADR-037) also count
against the five-comment budget, and their nits are dropped by the nit filter
(`packages/review/src/ranking.ts:60`).

### B4. An accepted runner result can be lost permanently

`apps/api/src/runner.ts:134-137` commits `RESULT_RECEIVED` in one transaction, then schedules
publication (payload insert and queue send) separately. If scheduling fails, the runner gets a 503.
Its retry is then treated as a duplicate (`duplicate:true`), which skips scheduling. Its failure
report gets `LEASE_LOST`, because the lease is no longer `LEASED`. The review is never published
and nothing retries it. Acceptance and scheduling need to be one transaction, or a duplicate must
re-schedule when no payload exists.

### B5. Only the first 20 changed text nodes of a pull request are reviewed, silently

`execute.ts:94` applies `.slice(0,LIMITS.nodeBatch)` to the whole set of changed nodes.
`nodeBatch` is the per-model-call batch size, which the pipeline already applies itself. As a
total cap it silently drops every changed node after the twentieth, and no diagnostic reports it.
That contradicts the architecture's rule that limits produce explicit partial coverage, never
silent success.

### B6. Repositories are only discovered from pull request events, and a missed installation breaks everything

- `installation` events record the installation but not its repositories, and
  `installation_repositories` events have no `repository`, so they are ignored as `no_repository`
  (`handlers.ts:42-58`). A repository appears in the admin API only after its first pull request
  or push event, and that first event is not reviewed, because the repository is still disabled.
- Repositories removed from the installation are never disabled.
- `repositories` has a foreign key to `github_installations`, and an installation row is written
  only by an `installation` webhook. If that delivery was missed (the App was installed before the
  endpoint existed, or the delivery failed), every later event for the account fails with a
  foreign-key violation, exhausts its retries and is dead-lettered. The `maintenance.webhook_recovery`
  job type exists, but nothing implements it.

## Major

### M1. Re-reviews pile up inline comments

Each push with findings posts a new pull request review (`packages/github/src/transport.ts:59`).
Only the no-findings summary comment is edited in place. Earlier inline comments are never
resolved, updated or removed, so a pull request with five pushes can show the same comment five
times. The `published_comments` and `publication_attempts` tables exist and are never written.

### M2. Publication is not idempotent under retry

The check run is created before the review (`transport.ts:39`). A failure after that point, or a
failure in `publications.discard` after a successful post (`apps/worker/src/publish-worker.ts`),
makes the queue retry and post a second check run or a second review.

### M3. Model output reaches pull request comments unescaped

`renderComment` and `renderSummary` insert the model's explanation as raw Markdown
(`publisher.ts:28-38`, `:92`). Content under review can therefore steer the model into posting
`@team` mentions (notifications to real people), links, images or HTML. The agent prompt block puts
the node's text inside a triple-backtick fence (`publisher.ts:58`), and the suggestion block does
the same with the replacement (`:34`), so text containing a code fence closes the block early. The
per-finding marker embeds the raw quoted text inside an HTML comment (`commentMarker`, with the
fingerprint built at `results.ts:21`), so quoted text containing `-->` closes the comment.

### M4. The summary-comment lookup trusts anyone's comment

`existingReview` takes the first of only 100 issue comments whose body contains the marker, from
any author (`transport.ts:29-33`). Any participant can post the marker. Humanize then tries to
edit or delete that person's comment, which fails and retries until the job dead-letters. On a busy
pull request, Humanize's own comment falls past the first 100, and the summary is duplicated.

### M5. Retrieved context can exceed the model's window by itself

`buildContext` defaults its budget to the entire model input budget (`retrieval/src/index.ts:120`,
12,000 tokens) and estimates four characters per token. The pipeline estimates two characters per
token (`packages/review/src/pipeline.ts:63`). One node with full context can therefore render to
roughly 24,000 estimated tokens, and `packBatches` still sends an oversized item on its own. On
Ollama, whose window is sized to the budget, the overflow is exactly the case the adapter warns
evicts the system prompt, which is the untrusted-content boundary. It needs a large repository to
trigger.

### M6. Failures never reach the pull request author

`review_runs` only ever moves from `RECEIVED` to `QUEUED`, on both paths. None of these produce a
check run or any visible signal:

- a lease that fails for good;
- a dead-lettered job (`packages/queue/src/index.ts:13`, retry limit 2, with nothing consuming the
  `.dead` queues);
- `invalid_result`, `no_credential` or `cloud_execution_unavailable`;
- a runner that lacks the configured model, which never claims the job
  (`packages/db/src/runners.ts:92`).

The author sees no review and no reason for it.

### M7. Declared limits are not enforced

`LIMITS.parserMs` (5 s), `parserMemoryMb` (256) and `jobMs` (30 min) are never read anywhere.
Extraction runs synchronously on the main thread with no timeout, and there is no overall job
deadline. pg-boss expires a job after 1,800 s (`queue/src/index.ts:13`), so a cloud review that runs
longer is retried while the first attempt is still running. The result is duplicate work and
possibly a duplicate publication.

### M8. Every review reads the whole repository

Per pull request, the executor clones the full history as a blobless clone, then reads every
supported file in the repository to build the context index (`execute.ts:62-84`). Each read is two
Git processes and, on a blobless clone, one lazy network fetch (`packages/scanner/src/git.ts:80-85`).
Each Git command has a 120 s timeout (`git.ts:49`). A repository with thousands of Markdown or
component files pays thousands of round trips on every push, and a large clone can fail outright on
the timeout.

### M9. The redacting telemetry is not used by any process

`@humanize/telemetry` implements the field- and shape-based redaction recorded in P1-S19. No app
imports it, and every production log line is a raw `console.log`. The redaction evidence is true of
the package, not of the running system. No OpenTelemetry tracing is wired either.

### M10. Built, tested and never called

These have no production caller: `LearningStore`, `FeedbackStore` and `RetentionStore`
(`packages/db/src/knowledge.ts`), `RunStore.storeFindings`, the `content-index` package,
`publishResult` in `apps/api/src/publish.ts` (a second publish path that duplicates the one in the
worker), `eventIntent` and `requireRepositoryAdmin`. Consequences:

- explicit learnings never influence a review;
- feedback is never recorded;
- no finding history is kept;
- `indexed` retention behaves exactly like `ephemeral`;
- nothing sweeps `webhook_deliveries` or `review_runs`, which grow without bound.

### M11. No dashboard

`apps/dashboard/src/index.ts` is `export {};`. Every administration step is HTTP only.

## Moderate

- **Configuration is read from the base branch tip, not the base commit.** `handlers.ts:97` passes
  `event.pull.baseRef` (a branch name), so the file can come from a newer commit than
  `snapshot.baseSha`. `configSha` also stores the blob SHA, although the field is labelled as a
  commit.
- **`allowDrafts` has no effect.** Draft pull requests are always skipped (`handlers.ts:72`), and the
  computed `effective.drafts` is never used.
- **Closed pull requests and new heads do not cancel or stale older runs.** A runner may review a
  superseded head. Publication then catches it as `StaleHeadError`, but the review work is wasted.
- **A busy runner shows as offline.** Heartbeats happen only between claims (`apps/runner/src/loop.ts:26`)
  and renewals do not touch `last_heartbeat`, so a runner in a long review reports offline after
  90 s.
- **Line numbers are computed quadratically.** `lineAt` scans from the start of the file for every
  node (`packages/extractors/src/core.ts:38`), so a 1 MiB file with 2,000 nodes costs billions of
  character comparisons.
- **The browser extension probably cannot reach the API (not run in Chrome).** The manifest
  declares no `host_permissions`, and the API sends no CORS headers, so a popup `fetch` with an
  `Authorization` header should fail its preflight.
- **Three provider adapters have never made a real call.** OpenAI, Gemini and OpenRouter are
  unverified. In particular, OpenAI strict structured output may reject the `minLength`/`maxLength`
  keywords that the Zod schemas emit.
- **The cloud executor is not idempotent on retry.** `schedulePublication` writes the payload, then
  sends the job. A failure between the two re-runs the whole review, model calls included.

## Minor

- **Uppercase file extensions are skipped.** Format detection is case-sensitive
  (`extractors/src/index.ts:26-32`), so `README.MD` is not reviewed.
- **Fingerprints drift across edits.** `stableKey` falls back to an emission index
  (`core.ts:33`), so inserting a string shifts the keys and fingerprints of everything after it,
  which also defeats de-duplication across re-reviews.
- **Ollama model list on every call.** The Ollama adapter lists models before every call
  (`packages/providers/src/ollama.ts:32`).
- **Retrieved quotes can split a character.** Retrieval quotes are cut at 600 UTF-16 units and can
  split a surrogate pair (`retrieval/src/index.ts:16`).
- **Session organization membership is fixed for 12 hours.** Writes re-check with GitHub; reads
  such as policy, the repository list and credential metadata do not.
- **The webhook delivery id is not signed.** A captured webhook can be replayed under a new id.
  Idempotent run creation makes the replay harmless today.

## What was confirmed working

- The canonical digest fix.
- Lease fencing, and database-clock liveness.
- Runner enrollment and ADR-028 authority. Serialization is proven by reverting the lock.
- Encrypted credential storage with rotation.
- Strict repository configuration parsing.
- Untrusted-content fencing and the quotation gate.
- Parser-safe suggestion proofs.
- The live Bedrock path.

The problems are almost entirely in how these pieces are joined, not in the pieces themselves.

## Suggested order of repair

1. **B1, B3 and B2 together.** They share one design change: the result envelope, or the snapshot,
   must carry what publication needs. That means the evidence's own nodes, the deterministic and
   blocking flags, and the effective review settings.
2. **B4, then M2 and M1.** Make acceptance-to-publication atomic, make publication idempotent, and
   update or resolve earlier comments rather than stacking new ones.
3. **B5, M5 and M7.** Enforce and report limits honestly.
4. **B6.** Record repositories from installation events, and reconcile installations.
5. **M3 and M4.** Escape published output and match only the App's own comments.
6. **M6.** Report failures to the pull request through the run-state machine.
