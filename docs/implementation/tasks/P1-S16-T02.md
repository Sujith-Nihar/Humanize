- Evidence: Repository enablement and organization policy administration implemented, exposed and consumed. The store performs the administrator check INSIDE the write, holding the target rows FOR UPDATE and only then asking which the caller may administer, so the answer cannot go stale and a revocation that lands first wins; six PostgreSQL tests prove selective enablement, the check seeing exactly the locked rows, a revoked caller enabling nothing, concurrent requests never overlapping inside the check, and a foreign repository never being offered. Organization policy has its own versioned, tenant-isolated table (migration 0005) kept apart from repository_configs so repository content cannot reach administrator-only fields (ADR-027). A REVIEW IS SKIPPED RATHER THAN DEFAULTED when no policy is set. ADR-028 NOW ENFORCED ON ORGANIZATION-WIDE WRITES (2026-09-29): previously PUT /api/policy, credential save and revoke, runner revocation and enrollment cancellation required only session membership, which is weaker than the approved decision. AdministrationStore.asOrganizationAdmin runs such a write only for someone who administers EVERY enabled repository, of which there must be at least one, with the check and the write in one transaction under a per-organization advisory authority lock that setEnabled also takes. The lock is advisory rather than a row lock because the protected thing is the enabled SET: enabling a currently disabled repository locks no row an organization check read. PROVEN BY REVERTING: with the lock removed from setEnabled, the serialization test fails because an enablement overtakes an in-flight organization check (expected [check:2], received [check:2, enable]); restored, it waits. Five new PostgreSQL tests cover full authority succeeding with the credential still ciphertext at rest, partial authority refused, no enabled repository refused, a failed write rolling back its credential insert, and serialization against enablement. Every privileged port now receives the acting user from the session, never the body. PUT /api/policy validates against OrganizationPolicySchema and refuses with INVALID_POLICY, because a stored policy that fails its schema silently skips every review; an unknown key such as an endpoint is refused by the strict schema. Authority refusals reach the caller by name, 403 NOT_AN_ADMINISTRATOR and 409 NO_ENABLED_REPOSITORY, and any other failure is answered without its text. GitHubIdentity (OAuth sign-in, user token dropped after exchange) and githubAdminCheck (fresh per-repository admin via a metadata-only App token, id-bound against renamed logins, fail closed) supply the production check.
