- Evidence: Encrypted provider credential administration implemented as write-only ingress, and NOW SERVED BY THE RUNNING API (2026-09-29). POST /api/credentials accepts a secret and returns only an identifier and provider name; a test saves sk-SENTINEL-VALUE and asserts the response body does not contain it, and the listing returns metadata only, so a saved secret is never readable through any endpoint (ADR-035). Saving and revoking are organization-wide writes under ADR-028: they run through AdministrationStore.asOrganizationAdmin, so only someone who administers every enabled repository may store or revoke a credential, and the insert happens inside the authority transaction so a failed write leaves no credential behind; a PostgreSQL test proves the value written that way is ciphertext at rest and still resolves. apps/api/src/admin-bindings.ts binds CredentialAdmin to EncryptedSecretStore, one store per provider because a credential resolves only for the provider it was saved for, with keys from cipherFromEnvironment rather than the database (spec 26.3). The binding refuses to register without HUMANIZE_ENCRYPTION_KEYS, because storing a secret unencrypted is not an available fallback. SMOKE-TESTED BY RUNNING THE BUILT API: unconfigured, it logs api.no_administration naming HUMANIZE_SESSION_KEY, GITHUB_OAUTH_CLIENT_ID, GITHUB_OAUTH_CLIENT_SECRET and HUMANIZE_ENCRYPTION_KEYS and /api/session is 404; configured, /api/session is 401 unsigned, /auth/github/start sets an HttpOnly Secure SameSite=Lax state cookie and returns a GitHub authorize URL carrying the client id and state and no secret, an unsigned PUT /api/policy is 401, and a forged OAuth state is 400.
